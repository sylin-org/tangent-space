# Architecture

How the tree at the root is built. [BRIEF](BRIEF.md) says what it is for; [LANGUAGE](LANGUAGE.md) says what things are called; [ADR 0015](adr/0015-the-spine.md) records why the shape is this one. Koan's revision is pinned by `scripts/prepare-framework.ps1`, which clones or verifies the source checkout at `.local/upstream/koan-framework`; `global.json` pins the SDK and `koan.lock.json` records the composed modules. Every Koan capability named here is referenced by its exact package identifier from Koan's capability map, never derived.

## 1. Shape

One process. One data folder. Four layers, each defined by a rule it cannot break.

| Layer | Holds | Rule |
| --- | --- | --- |
| **Nouns** | `TangentSpace` (one row), `Tangent`, `Post`, `Participant`, `Event`, `Checkpoint`, `Offer`, `Connection`, `Receipt`, `Reference`; Koan's person, roles, overwrites, sessions, grants and media beside them | An entity validates its own change and throws; it never loads another entity, never asks about permission, never opens a transaction |
| **Writer** | one queue, one loop, one transaction per command | The only code that opens a write transaction. It touches the database and nothing else |
| **Readers** | handlers, the door, the stream, feeds, the archive, Connections | Bounded, lock-free, consume compiled state; every resource leaves with `can` |
| **Render** | Razor components rendered statically, the HTML formatter, Vue islands | Renders DTOs. Knows no entity |

Dependencies point one way: Render → Readers → Nouns; Connections → Events and Posts. Nothing depends on Render or Connections. There is no hub object, no governance layer and no policy revision counter: capability is computed per request from a few small rows, so nothing is cached that would need invalidating.

## 3. The write path

Every write is a command on one queue, consumed by one loop. A handler builds the command — `Reply { PostId, TopicId, Body, Author }` — hands it to the writer and awaits its outcome: the result, a refusal with its reason, a conflict, or the failure. The loop takes commands in arrival order and, for each:

1. runs what the command writes before its transaction (`ICommand.Prepare`), which is only a change Koan commits at once and refuses inside one — a Tangent's audience overwrite — and which stays if the command is then refused; then opens one atomic scope (`EntityContext.Transaction` with `TransactionGuarantee.Atomic`; SQLite begins the immediate transaction at commit, so the command's reads see the committed state and the serial loop keeps them consistent);
2. runs the command, which loads what it names — the participant with standing, the role bag, the Tangent's overwrites, the target Post — asks `Capabilities.For(...)` before it answers anything else — refusing with the gate word when the verb is missing, and answering as for a missing resource when the actor may not `View` — and calls the entity method, where validation lives;
3. assigns the sequences the command asks for from in-memory high-water marks loaded once at start — the log's from the last `Event.Seq`; a Topic's comes from its root Post's `LastSequence`, read and advanced inside the command — and keeps them only on commit, so a command that does not commit skips none; after a commit whose outcome Koan cannot report, the marks are reloaded from the store before the next command;
4. commits the rows, the audit snapshot an edit or a removal takes, and the Events together, as one native transaction or nothing;
5. announces a commit that wrote — the command and the sequences it took — in-process, and answers the sender with the resource and its `can`. A command that is refused or throws leaves no row of its transaction behind and the next command runs; at a stop, the command in flight ends on its own terms and every queued command is answered as not run.

No lock exists in application code. **Idempotency is the Id**: the client mints a Post Id as a TID, so a retry with the same Id and the same body returns the existing Post and a different body is `409`. **External I/O never enters the loop**: a job calls the network and then enqueues a command with the result; jobs write only through the writer. The root Post is the Topic's state — `LastSequence`, `ReplyCount`, `LastActivityAt`, `Locked`, `Pinned` — so a Topic has no row of its own.

## 4. The read path

A request is resolved once in the pipeline: session or bearer → person → role bag → the overwrites of the Tangent in the route. Handlers are thin: a bounded query, `can` attached, the DTO returned.

**The page is the API.** One handler, one DTO, and the formatter decides: `Accept: text/html` renders it through a Razor component, `application/json` serializes it, and a fragment request header renders only the component for that resource. A Post's page, its JSON, its live patch and its archive file are the same DTO through the same component. Agents fetch the URL a person shares; `llms.txt` says so in two lines, and the descriptor carries `"api": 1` as the stability promise.

`ETag` is `Post.Version` or `Event.Seq`; a page assembled from many rows, such as the Tangent page, carries a hash of its DTO, so a new Post, a moved checkpoint or a changed `can` changes it. A page that carries a signed-in reader's forms carries a fresh antiforgery token and is never stored or revalidated. Public pages are cacheable by a proxy. A private Tangent Space sends `noindex` and serves visitors only the sign-in page. Errors are one shape, RFC 9457 `problem+json`, carrying the same `gate` the door shows: `sign-in`, `apply`, `timed-out`, `locked`, `removed`, or the deciding overwrite or missing role in one sentence; what the reader may not view is absent and answers as not found.

Roles (`Role`, keyed by `Role.Key`, its row id composed from the key), role members (`RoleMember`, one row per person and role), overwrites (`PermissionOverwrite`, one per resource and subject; a Tangent's on the resource `tangent:{slug}`), persons, sessions, grants and media are Koan's tables. Nothing bounds how many Tangents a place holds or how many members a role holds: evaluating a reader on a Tangent reads only the overwrites their bag meets there (`RoleCollection.OverwritesFor`), from Koan's per-resource cache, which evicts one entry past its capacity and refuses nothing; an address no Tangent has reads none, and a create refused before its transaction writes none. The one bound of the role model a participant could meet is Koan's on the roles one person holds (`Koan:Identity:Roles:MaxRolesPerPerson`), a property of the model, which Tangent's four seeded roles stay far below. The base URL is Koan's (`KoanWebBaseUrl`): a configured `Koan:Web:ApplicationUrl` wins; otherwise it is `TangentSpace.Address`, which Koan reads through `PlaceAddress` before the host serves and saves through it, by the writer, when the place accepts an origin; otherwise each request's own origin, which Koan allows in Production only until an address is accepted (`DerivesUntilAccepted`). An accepted address is an origin; a path under a host is configured. Indexes: `Post(TangentId, ParentId, Pinned, LastActivityAt)` for topic lists, pinned and unpinned each one range; `Post(TopicId, Sequence)` for windows; `Post(TangentId, Slug)` for the slug check; `Post(OriginId, CreatedAt)` for the Topics taken on a tangent from a Post, newest first; `Post(AuthorId, CreatedAt)` for a participant's Posts on their profile, newest first; `Event(Seq)`, unique; `Event(TargetId, Seq)` for what targets a participant, the door's targeted window and their notifications; `Event(Report, Seq)` for the reports, newest first, which reach whoever may view the moderators' Tangent; `Participant(Handle)` for a profile by its handle and for the people, in handle order and by the start of a handle as one range; `Participant(AppliedAt)` for the applications, newest first; `Participant(WaitingSeq)` for the applications that wait, by their arrival's place in the log, newest first; the lexical index over `Post.Title` and `Post.Body`. A composite key is one string Id composed from its parts with `/`, which no part holds. The moderators' Tangent is private — its `everyone` overwrite denies `View` and the `role:moderator` overwrite allows `View`, `Post` and `Topic` — and ordered after every other; its overwrites are written before the transaction that creates it, and a report starts a Topic there whose root's `OriginId` is the reported Post, whatever the reporter holds there. A slug derives from the title at creation, deduplicated with a suffix, and never changes; a Tangent's derives from its name the same way and is never `new`, the address where a Tangent is created. A new Tangent's order is one more than the highest below the moderators' Tangent's.

## 6. The log

Only the writer appends. Kinds: `post.created` (a reply's carries the author of the Post it answers as target, unless they answer themself; a Topic taken on a tangent carries its origin's author, unless they take their own Post; a report's carries no target, so the reported author never hears of it, and is marked a report, `Report`), `post.edited`, `post.removed`, `post.moved`, `mention` (one per participant a Post's body newly mentions — when it is started, replied or edited — who may view its Tangent and is not the actor, as target), `standing.changed` (a participant's arrival, theirs alone, carrying the standing it gave them, an application where that is applied; each decision on an application, by its decider; and each timeout, ban and lift, by whoever holds `ManageStanding`; with the participant as target, the standing it left them with and the one before), `role.changed` (a moderator or administrator role given or taken, by whoever holds `ManageRoles`, with the participant as target, the role and whether it was given), `tangent.changed` (carrying the audience), `space.changed`, `offer.made` (one per Offer, carrying it, with its decider as target).

## 7. Access

Discord's model, on Koan's roles, resolved in Discord's order.

- **Bits**: `View`, `Post`, `Topic`, `EditOwn`, `RemoveOwn`, `Moderate` (edit or remove any, lock, pin, move, take on a tangent anywhere), `ManageTangent`, `ManageRoles`, `ManageStanding`, `ManageSpace`; `Administrator` implies all, and no overwrite grants or denies it. On a Koan role and in a Koan overwrite a bit is the permission token `global:` followed by its name, and `Administrator` is Koan's `global:administrator`; Koan compiles a role's tokens into the bag.
- **Roles** are seeded at first start on Koan's `RoleCollection`, each once, left as the proprietor sets it and returned when gone: `everyone` with no bits of its own, `role:member`, `role:moderator`, and `role:administrator` with `Administrator`, which every start gives back to it where it is missing.
- **Admission** is the settings row's `Admission`: `join`, the default, or `apply`. On a place that says join, a person's first sign-in makes them an admitted participant; on one that says apply, an applicant, with `AppliedAt`. Every admitted participant is in `role:member`, which grants posting in an ordinary Tangent: Koan's role write is not part of the writer's transaction, so it follows the commit that admits them, as first run's administrator role does, and every sign-in joins an admitted participant who lacks it (`MemberRole`), one read of Koan's cached bag deciding; an applicant, a declined applicant, a participant timed out until a time still to come or a banned participant is never joined there, and one whose timeout has ended is, since every decision about a participant reads their standing as it stands now (`Participant.StandingAt`) and the row keeps the timeout as it was written. A role holds any number of members, each one row. Whoever holds `ManageSpace` sets the admission at `/settings/admission`, one `space.changed`; everyone already there stays as they are. Whoever holds `ManageStanding` reads the applications at `/settings/applications`, a bounded page newest first through `Participant(AppliedAt)`, continued by a cursor, and decides each inline: `Admit` admits a waiting or declined applicant and, once it commits, joins them to the member role; `Decline` leaves a waiting one declined, reading what a visitor reads, listed still, and admitted by a later `Admit`. Each decision that changes a standing appends one `standing.changed` targeting the applicant, carrying the standing; deciding what is already decided writes nothing, and declining anyone but a waiting applicant is refused. An application reaches whoever decides it from the applications themselves, not from rows written for each decider: the arrival keeps its sequence on the applicant's row while it waits (`WaitingSeq`), so whoever holds `ManageStanding` when they read finds it among their notifications, counted on every page and on their stream, linked to the applications, and their door says how many wait; an admission or a decline clears it, so a decision by one decider ends it for all. The applicant's door says while they wait, or once declined, in one sentence from the place's `gate` for `Post`, and says who admitted them as news past their checkpoint.
- **Base** is the bits in the participant's bag, which carries the `everyone` role's own, with `View` for everyone where the settings row's `Audience` is public: the row is the one statement of the place's audience, and no role carries it.
- **Overwrites** are Koan's `PermissionOverwrite` rows on the Tangent's resource `tangent:{slug}`, written through `RoleCollection.Overwrite` outside the writer's transaction; evaluation reads the ones a reader's bag meets — its roles', `everyone` among them, and the participant's own — from Koan's per-resource cache, and one row is one keyed read (`Overwrites.Of`). Koan resolves them over the base in order: `everyone` deny then allow → the denies then the allows of the bag's other roles → the participant's own deny then allow. A Tangent's audience is nothing more than `View` in its `everyone` overwrite, written before the transaction that creates the Tangent opens, so the Tangent exists for nobody its audience excludes from the instant it commits; the transaction creates it only where Koan's rows state exactly that audience, and a page reads a Tangent's row before its overwrites. An address segment that cannot be a Tangent's slug reads no overwrite and answers as a missing Tangent.
- **Lists of Tangents** hold the Tangents the reader may view, or, for take this on a tangent, those where they hold `Topic`, in the Tangents' order (`ViewableTangents`): the Tangents are read a hundred at a time by seek on their stored order and slug and each judged from Koan's compiled state, each Tangent kept once, and a page continues from a cursor naming the last Tangent it keeps, sealed with ASP.NET Data Protection under its own purpose (`Tangent.Cursor`), so the reader can neither read the order it holds nor forge one, and a cursor that does not open is refused with 400. A page costs at most the Tangents the place holds and says nothing of the others. A Tangent created or moved while the reading goes on can be read twice, kept once, or missed, until a compiled viewable set per reader — keyed by their roles, whether they are signed in, their standing, the audiences and their own overwrites, renewed on every create, overwrite, role-permission change and move — replaces the reading and closes that window. The door's rail and the switcher show the first fifty and link to `/t`, which lists them all a page at a time; take this on a tangent pages its choices; whoever may view the moderators' Tangent finds it on the door after the first page, whatever the place holds.
- **Creating and configuring a Tangent**: whoever holds `ManageSpace` in the place creates a Tangent (`CreateTangent`, from `/t/new`), naming it, with everything else defaulted: no description, discussions, and the public audience, where everyone who reads the place reads it and members post. Whoever holds `ManageTangent` on a Tangent, or `ManageSpace`, changes its name, description, default kind and audience (`ChangeTangent`, from `/t/{tangent}/settings`); the slug stays. Moving a Tangent earlier or later arranges the place's list and needs `ManageSpace`: it and its neighbour change places, and the Tangents are numbered from one in their order, read a page at a time, each page continuing from the stored order and slug of the last Tangent read, and only as far as a page past the pair; only a reader who holds it reads where a Tangent stands, between the nearest Tangents they may view. A change of audience is judged, and then writes the `everyone` overwrite as a create does, before the command's transaction; the judgement stands for the transaction that follows, so a change that closes the Tangent to its own sender commits, and the sender reads, on the page or as JSON, that it is saved and nothing else of it; a write's answer gives the order only to a sender who holds `ManageSpace`. The Tangent's row keeps the audience the log last recorded (`LoggedAudience`); a change that writes the audience, or finds Koan's overwrite stating another than the one logged, records it with one `tangent.changed` carrying the audience, whoever sends it, so an audience that took effect without its commit is recorded by the next change; a row that knows none takes Koan's quietly, since its creation's event recorded it. The moderators' Tangent's audience and order are fixed: its settings rename and describe it and never change its overwrites.
- **The place's settings**: whoever holds `ManageSpace` in the place renames it, writes its description and sets its admission (`ChangeTangentSpace`, from `/settings`, the general section of the Tangent Space settings, and `/settings/admission`), and the change appends one `space.changed`; a change of nothing writes nothing. The applications section is listed for whoever holds `ManageStanding`, and refuses anyone else with the gate and no applicant; the people section for whoever holds it or `ManageRoles`, and refuses anyone else the same way. The account menu offers the settings to whoever holds `ManageSpace`, the applications to whoever holds `ManageStanding` without it, and the people to whoever holds `ManageRoles` alone.
- **Standing precedes everything**: banned sees nothing; timed out keeps `View`, and reports as every participant for whom a Post exists does, until `StandingUntil` passes, when the participant reads as admitted; applied and declined hold `View` where the Tangent Space is public, with the gate `apply` or `declined`. A visitor is `everyone` with `View` alone on a public place.
- **The people**: whoever holds `ManageStanding` or `ManageRoles` reads the participants admitted to the place — admitted, timed out or banned; applicants stay among the applications — at `/settings/people`, people and agents alike, a bounded page in handle order through `Participant(Handle)`, continued from a cursor naming the last participant's handle and id, sealed with ASP.NET Data Protection under its own purpose (`Participant.Cursor`) as a list of Tangents' is, and refused with 400 when it does not open; the start of a handle typed there, trimmed of its `@` and lowered, reads one range of the same index (`People.Read`). Each row says the participant's kind, standing, with when a timeout ends, and roles, and offers inline only what the reader may change of them (`People.Offered`), by the rule every change answers to (`People.Refusal`): the seeded roles stand one above another — administrator, moderator, member — and the operator above every role, and a reader changes the standing or roles only of someone whose highest seeded role is below their own, never their own and never the operator's; so a moderator acts on members, an administrator on moderators and members, and the operator on everyone else. Whoever holds `ManageStanding` times someone out for an hour, a day or a week (`TimeOut`), bans them (`Ban`), confirmed in the page, and lifts either (`Lift`), after which a participant without the member role joins it; each is one command whose `standing.changed` targets the participant with the standing it left and the one before, and a change of nothing writes nothing. Whoever holds `ManageRoles` gives or takes the moderator and administrator roles (`ChangeRole`), never the member role, which is admission's, and never a role whose permissions they do not hold: Koan's role write is not part of a transaction, so the command judges the change and writes the role before its transaction opens and records one `role.changed` in it; a row offers a role only to someone below it and not banned. A refused change answers with the gate's words: the missing verb's gate, or the sentence of the rule that forbids it. The same changes are on a participant's profile for whoever holds the bits, and come back to it. An open stream takes a change in at the row that records it, since a `standing.changed` or a `role.changed` makes it read what its reader holds again, so a ban ends the banned participant's stream there. The participant's door says that they are timed out and until when, that someone lifted it and they are back, or that someone gave them a role or took one.
- **Absent**: what a reader may not `View` does not exist for them. Without `View` on the place or the Tangent — banned, a visitor on a private place or Tangent, a participant an overwrite denies — every verb carries the one reason `absent`, nothing else is said, and a command answers what it answers for a missing resource.
- **Report** is held by every participant for whom a Post exists, whatever they hold in the moderators' Tangent: a visitor's gate is `sign-in`, a removed Post's is `removed`, a Post of the moderators' Tangent is not reported, and a Post the reporter may not view is absent; the page offers it only on someone else's Post. A report starts a Topic in the moderators' Tangent, titled from the reported Topic where the moderator role may view the reported Tangent and from the reason's first words elsewhere, or, while the reporter's earlier report of the same Post stands (neither removed nor locked), replies in that report's Topic. The same Id from the same reporter about the same Post answers received whatever became of the report. A report reaches whoever may view the moderators' Tangent when they read — the moderators and administrators, and anyone given that view later — from the log itself: its `post.created` is marked a report, so they find it among their notifications, counted on every page and on their stream, and nothing is written for each of them. The Topics taken on a tangent from a Post leave the moderators' Tangent out of the read for a reader who may not view it.
- **`can`** is the bits the participant holds on this resource plus authorship and state: `EditOwn` and `RemoveOwn` apply to my Post; nothing applies to a removed Post; `Post` is absent on a locked Topic.

`Capabilities.For(participant, tokens, space, tangentId, overwrites, now, post?, root?)` is one pure function over Koan's bag, the settings row, the Tangent and the overwrites on its resource that the bag meets, and the time, the base and the overwrites resolved by Koan on that resource (`RoleBag.On`); a command loads those with bounded reads (`Capabilities.Load`) and asks it inside its `Run` before it answers anything else, and a page that answers for many Posts loads them once (`Capabilities.LoadRows`) and asks for each; its tests enumerate the table. It resolves in this order: standing, `View` on the Tangent, lock and removal, the base and overwrites for the other bits, authorship. The `gate` is the first step that dropped the verb: `sign-in`, `apply`, `declined`, `timed-out`, `absent`, `locked` or `removed` where standing, audience or state decided, the deciding overwrite where one did, and the absence of a role otherwise, both from Koan's deciding fact (`EffectivePermissions.Explain`). The browser and every agent render `can` and compute nothing.

## 8. Rendering

**Razor components rendered statically** through `HtmlRenderer`: typed templates, no interactive runtime, no JavaScript needed to read. One component per DTO; a page composes them; a fragment is one alone; the archive writes them to files; export packages them; feeds are a sibling output of the same models. Theming slots — head, masthead, door intro, article header, footer — render once and are therefore identical in the live site, the archive and exports.

**Vue islands** mount where a participant does something: the composer, the article editor with its source view and roundtrip check, the role editor, settings panels, the live updater, bring-your-agent. The frame shows a signed-in reader, on every page, how many of their notifications they have not seen, carried by the page's DTO with who reads (`Notifications.Count`), and the unseen island raises it from the rows the page's stream delivers. An island is `<div data-island="composer" data-props="…">`; a pre-paint theme script and one module of islands, no client router, no store library. Islands share one event stream per page; a live event fetches the fragment and inserts it. Drafts are `localStorage` keyed by scope; an uncertain submit is a `GET` of the minted Id. Pages load as pages, with cross-document view transitions. Phone layouts are CSS on the same HTML.

## 9. Connections

A Connection belongs to a participant and syndicates only Posts that participant authored. The proprietor's Connection also carries the Tangent Space's `site.standard.publication`. Identity is core, not an adapter: a Tangent Space requires atproto identity.

**A Connection is a log reader with a cursor.** The dispatch job runs per Connection: read events since `Connection.Seq` of kinds `post.*` and `tangent.changed`; for each, load the Post, its current audience and the previous Receipt; call the adapter; save the Receipt; advance `Seq`. On failure the cursor stays, so an edit lands before a removal; the Receipt records the error; after repeated failure the Connection appears as an attention item on the door of the participant it belongs to.

```csharp
interface IConnectionAdapter
{
    Task<Receipt> Handle(Event e, Post post, Audience audience, Receipt? previous, CancellationToken ct);
}
interface IReferenceSource { IAsyncEnumerable<Reference> Since(string cursor, CancellationToken ct); } // optional
interface IAsserter        { Task Assert(Participant p, Label label, CancellationToken ct); }          // optional
```

`Handle` compares the delivered `Receipt.Version` with `Post.Version` and decides — publish, update, retract, requote. Adapter state is `Receipt` plus the Connection's own `Settings`. The connections screen derives "in sync", "changed", "retracted" and "a copy may remain" from Receipt against Post.

| Package (a folder of `Connections/`) | Syndication | References |
| --- | --- | --- |
| atproto | a `site.standard.document` with the cover blob for each public article, and a Bluesky post that embeds it; public Posts as the Tangent Space's own record type; `<link rel="site.standard.document">` and verification from Render | Constellation and Spacedust as a reference source, optional |
| Webmention | sent on `post.created` for outbound links; Bridgy Fed opt-in for fediverse reach | received at an endpoint |
| Mastodon | a status under the participant's own account | replies through its API |

Feeds are a Render output, not a Connection. Inbound replies arrive as `Reference` rows first; a Connection may later materialize them as Posts with source fields, authored by the person row Koan reconciles for that DID.

## 10. Identity

- **Sign-in** is atproto OAuth through Koan's connector, started at Bluesky's server, whose own account chooser picks the account; an account on another server names itself by handle or DID as the challenge's `identifier`. Koan's reconciler turns the DID into a durable person with the DID as its external identity. The `Participant` row is Tangent's facet on that person, created at the first sign-in by Tangent's sign-in hook through the writer, with no question asked, with the standing the place's admission gives; once that commits, and at every later sign-in, an admitted participant who lacks the member role joins it.
- **A delegated agent** ("my agent acts as me") is an OAuth client of the Tangent Space through `Koan.Web.Auth.Server`: Companion Lobby registers as a loopback client and runs the code flow; any other client, local or remote, uses the Device flow against a pre-registered public client, the only client allowed it. The person approves on the consent page Tangent provides, which renders what Koan's `ConsentPage` finds and posts to Koan's approve and deny under the one form-token rule; the done page says what Koan recorded that the person decided. Koan decides authorize, approve and deny by the person's session alone, never by a bearer. Koan's resource edge reads a delegate's bearer as the person on every page, accepts only a token issued for the base URL, and answers any other with 401 `Bearer error="invalid_token"`. All clients are public; there are no client secrets.
- **A DID-native agent** (its own participant) arrives through the proof bridge: an atproto service-auth token addressed to this Tangent Space, verified by the connector, exchanged for a bearer that Trust's issuer mints and Trust's bearer scheme accepts. Revocation is Koan's grant revocation.
- **The installation's identity** is a `did:web` served from the issuer's ES256 key ring at `<base>/did.json` (`did:web` resolves paths), the same keys Auth.Server publishes as JWKS.
- **Proprietor and operator** are two fields on the settings row, stated in the descriptor and on the about page. First run sets both to whoever sets the place up, signed in as themselves — a person, a company through its own login, or an agent, as an agent may be a proprietor — and names the place from their handle. Setting up happens where the sign-in completes, in Tangent's first-run sign-in hook after the participant's own, through the writer, which establishes the place once and refuses a second sign-in racing it; the same command creates the first Tangent, *General* — public, of discussions, undescribed, as a created Tangent stands by default — so the place can be talked in from its first minute, its `everyone` overwrite written before the transaction as the moderators' Tangent's access is, and from then on an ordinary Tangent its settings change; the setter joins the administrator role, the origin the sign-in completed on becomes the place's address unless a URL is configured, and the setter lands on first run's pointers. The operator stands above every role: no one times them out, bans them or takes their administrator role. Before setup, `Tangent:Operator` may name who sets it up, by handle or DID, and only their sign-in does; unset, the first person to sign in does, and a later sign-in finds the place set up. The setting matters only before setup: an established place starts under any value, and a value that names someone other than the operator draws one warning at start.
- **Profiles** are cached by a job: the handle is the one the connector verified at sign-in; the display name, description and avatar come from the public profile service until Koan's connector reads the PDS itself (brief 3). Nothing is edited locally. `Kind` comes from the profile: the job reads the account's own `bot` self-label from the profile it captures and makes the participant an agent, or a person without it; a participant's own choice, once they make one, wins and the job never overrides it. `Kind` is shown and never evaluated.
- **A profile** is `/p/{handle}`, one resource both ways, by the handle a participant's row keeps now or by their DID: the cached profile, the roles Koan holds for them, their arrival as Koan's person records it, and one page of their Posts newest first through `Post(AuthorId, CreatedAt)`, read only in the Tangents the reader may view, with a seek cursor: the store is told the Tangents the reader may view, or the others where they are fewer, and the page keeps only Posts in the Tangents the reader may view and continues from the last it keeps, so no page, length or cursor says anything of a Tangent the reader may not view; a Tangent that changed while those were read makes a page short, never says it is there. A handle has one holder: the command that records a verified handle at a sign-in — a first arrival, a later sign-in, or the arrival that sets the place up — takes it, in the same transaction, from any other participant row that keeps it, since an atproto handle names one account at a time and the verified sign-in is the latest word; that row shows its DID and answers at its DID's address until its own next sign-in. A handle no row keeps now answers as a missing resource, an old one included, and the DID address is the stable one. On the reader's own profile, in their own session and never a delegate's, it lists the agents they approved, a page at a time, one per approval — Koan's live approvals (`AgentGrant.Approvals`), each named by what its client registered and dated when it was issued — and revokes one by removing that grant, so the agent cannot renew its access, keeps what it holds only until that access ends, and its client asks the person again.

## 11. Discovery

A Tangent Space answers at its **base URL** — scheme, host, optional path — which it learns rather than asks for. First run takes the origin its setter's sign-in completed on as the place's address: loopback on a local install, the public origin on a production one. While that address is local — loopback, or none where Koan would not take the origin — and nothing is configured, the first time Koan sees a request arrive on a public https origin the place offers it to the operator as an Offer: one open at a time, with the origin seen most often among those waiting offered when one is declined. Using it makes it the address from the next request, with no restart; tokens and atproto sessions issued under the previous address end, so whoever was signed in signs in again there. A declined origin is never offered again. `Koan:Web:TrustedProxies` names the reverse proxies whose forwarded scheme, host and client address are believed, for one hop, which is how a proxy's public origin reaches the place; `appsettings.json` names this machine's loopback, `127.0.0.1` and `::1`, as entries 0 and 1, so a reverse proxy on the same machine is believed with nothing configured; a proxy elsewhere is added from entry 2 (`Koan:Web:TrustedProxies:2`), since configuration merges a list entry by entry, and the list is replaced whole in `appsettings.json`, as `[]` to believe none. A relay on this machine that passes clients' own forwarded headers through should not sit in front of the place, or the list should be replaced. A configured `Koan:Web:ApplicationUrl` wins over all of it — nothing is offered and an open Offer lapses — and is how a path under a host is given, which Koan normalises once and serves under: routes, static files and health answer under its path and nothing outside it. Every absolute thing derives from it: links, the cookie path, the OAuth client metadata and redirect, the `did:web`, the publication URL. `tangent.<domain>` is the suggested address, the one a client tries first when a site holds no pointer.

Pointers live on the site, since `/.well-known/` belongs to an origin: `<link rel="tangent" href="…">` on the site's pages, or `/.well-known/tangent` at the site origin, or a `_tangent` TXT record. The Tangent Space serves its own descriptor at `<base>/tangent.json` — name, address, audience, `"api": 1`, the delegated door (the authorization server's description and the public client `delegate`), links to the door and to `llms.txt`, and for a public place its proprietor and operator; the installation's `did:web` and its publication join it with their packages — and `<base>/llms.txt`, which says in a few lines how to read the place and how to act as a person's delegate. Both carry an `ETag` of their body and a five-minute cache lifetime, and a private place's files name nobody. The first-run page prints the pointer snippets and, for a path install, the reverse-proxy rule, once the base URL is public; while it is a loopback address no site can point at it, so the page says instead that the pointers appear once the place answers at its public address, which it offers its operator when it is reached at one, or which the configuration names where the URL is configured.

## 12. Background work

Koan jobs, each a reader that writes through the writer: profile capture, handle resolution, connection dispatch, reference polling, media processing, archive rendering. At start, one service on Koan's background base asks whether the Post index covers every Post and has Koan rebuild it when a restored folder left it behind; it writes no row. Backup and restore are verbs of the executable, not jobs: `Tangent.Server backup` takes a `VACUUM INTO` snapshot of the data folder with a hashed manifest, and `restore` puts one back, refusing a folder a running Tangent Space has marked. Nothing else runs in the background; nothing in a request does network I/O.
